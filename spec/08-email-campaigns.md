# Email Campaigns

This document defines the Phase 4 invitation-email workflow. The functional requirements in [02-functional-requirements.md](02-functional-requirements.md) remain normative.

## Scope

Email delivery is a manually approved campaign workflow. It sends party-specific invitation or reminder messages through a replaceable provider adapter, beginning with Resend. A campaign is not RSVP state: provider or delivery failure must not change a party's RSVP eligibility, status, deadline, or capacity contribution.

This scope covers sender configuration, templates, preview/test send, manually triggered batch campaigns, resend/retry behavior, durable dispatch records, and delivery-status UI. Ticket, seat, and theater handoff messages remain out of scope.

## Current State

The current application has campaign-preparation prerequisites, but no provider delivery worker.

Implemented:

- A committed batch creates an active `RsvpToken` hash for each party.
- The corresponding raw token is retained only in a protected delivery envelope for a future send worker.
- A token may be regenerated by an `ElevatedOperator`, revoking the prior active token.
- Organizer batch, party, audit, and settings routes exist.
- Elevated organizers can configure sender identity, Reply-To, daily send ceiling, and the operational sender-domain verification marker. API keys remain outside the UI.
- Operators and elevated organizers can create and approve versioned templates.
- Operators and elevated organizers can prepare an initial-invitation campaign for one eligible committed batch.
- Campaign preparation creates durable, immutable recipient dispatch snapshots before any provider request is attempted.
- The Email campaigns route lists campaigns, creates and approves templates, and prepares initial-invitation campaign snapshots.

Not implemented:

- Resend API adapter, API-key configuration, provider rate limiting, or provider delivery worker.
- Message rendering, preview, test send, reminder/resend preparation, or provider webhooks.
- Suppression persistence and party-level delivery-status UI.

### Current UI Gaps

The first campaign screen is a persistence foundation, not a final send workflow. Resolve these before enabling provider delivery:

- Fix literal display defects such as `template @campaign.TemplateVersionNumber` and `InitialInvitation v@template.VersionNumber`; render actual version numbers and human-readable campaign/template types.
- Change the first preparation action from `Queued` to `ReadyForReview`. A campaign must not appear queued until an organizer gives final confirmation.
- Replace campaign summary rows with a campaign detail/review route containing recipient, sender, template, and dispatch snapshot information.
- Add template placeholder guidance, supported-placeholder validation, starter invitation content, and separate HTML/plain-text preview.
- Add a controlled test-send workflow before any campaign can be confirmed for guests.
- Persistent managed Data Protection key storage for production delivery envelopes.

The current Resend free tier is not a production launch assumption. At the time this specification was recorded, Resend documents a 3,000-email monthly allowance and a 100-email daily limit on its free transactional plan. The planned event requires an upgraded account before launch; current provider limits must be rechecked immediately before sending.

## Delivery Phases

The phases below are implementation gates. Do not skip a phase merely because persistence for a later phase exists.

| Phase | Status | Outcome | Required work |

| E1: Review and rendering | In Progress | An organizer can safely inspect representative rendered content and explicitly queue a campaign. | Controlled provider-backed test send remains to be added. |

## Campaign State Machine

Use these states consistently in persistence, UI, and audit records:

```text
Draft -> ReadyForReview -> Queued -> Sending -> Completed
                         -> Cancelled    -> PartiallyFailed
                                         -> Failed
```

- `Draft`: campaign metadata may still change; no immutable recipient snapshot exists.
- `ReadyForReview`: template, sender, batch/scope, recipient snapshot, and skipped-recipient reasons are frozen for organizer review. No provider call is allowed.
- `Queued`: an operator explicitly confirmed the reviewed campaign. Dispatches are eligible for worker claim.
- `Sending`: one or more dispatches are actively leased or being processed.
- `Completed`: every dispatch reached its final successful provider state available at the current phase, initially `Accepted`.
- `PartiallyFailed`: at least one dispatch has a terminal failure and at least one has been accepted/delivered.
- `Failed`: no dispatch completed successfully or the campaign cannot proceed due to a terminal configuration failure.
- `Cancelled`: a reviewed, not-yet-sent campaign was explicitly cancelled. This requires confirmation and audit.

Campaign preparation creates a `ReadyForReview` campaign. Only final confirmation transitions it to `Queued`.

## Sender Configuration

Add an elevated-only Email settings area to `/organizer/settings`.

| Field | Rules |
| --- | --- |
| From display name | Required, organizer-visible display text. |
| From address | Required, syntactically valid, and from a verified Resend domain. |
| Reply-To address | Required, syntactically valid, monitored mailbox. |
| Daily send ceiling | Required positive limit, lower than or equal to the approved provider limit. |
| Provider | `Resend` initially, behind an adapter interface. |

The Resend API key must be supplied through protected application configuration, for example `Resend__ApiKey`, and must never be stored in the database, rendered in the organizer UI, logged, or included in audit events.

Before a campaign can be approved, validate that sender configuration is complete and that the configured From domain has been operationally verified in Resend. Domain verification itself remains an external Resend/DNS operation.

## Templates

Persist versioned application-owned templates rather than depending on mutable provider-hosted content.

### `EmailTemplate`

| Field | Notes |
| --- | --- |
| ID | Stable internal identifier. |
| Type | `InitialInvitation` or `Reminder`. |
| Version | Immutable incrementing version per template family. |
| Subject | Renderable subject line. |
| HTML body | Required HTML representation. |
| Plain-text body | Required intentional plain-text representation. |
| State | `Draft`, `Approved`, or `Retired`. |
| Creator/approver metadata | Authenticated actor and UTC timestamps. |
| Content digest | Supports reproducibility and audit. |

Approved templates must include event identity, party allocation, deadline with time-zone label, RSVP URL, and support contact. Escape all imported/guest-provided data for HTML, plaintext, and URL contexts. Never expose internal IDs when the opaque RSVP token is sufficient.

Template preview must support long names, diacritics, one-seat parties, multi-seat parties, and both HTML/plain-text views.

## Campaign And Dispatch Model

### `EmailCampaign`

One manually approved send operation.

| Field | Notes |
| --- | --- |
| ID | Stable campaign reference. |
| Type | `InitialInvitation`, `Reminder`, or `Resend`. |
| Batch or explicit scope | Initial invitation normally selects one committed batch. |
| Template ID/version snapshot | Immutable approved version used for rendering. |
| Sender snapshot | From display name/address and Reply-To at approval time. |
| Creator/confirmer metadata | Authenticated actor and UTC timestamps. |
| State | `Draft`, `ReadyForReview`, `Approved`, `Queued`, `Sending`, `Completed`, `PartiallyFailed`, or `Failed`. |
| Recipient summary | Prepared, skipped, accepted, delivered, failed, bounced, complained, suppressed counts. |

### `EmailDispatch`

One immutable campaign-party recipient record.

| Field | Notes |
| --- | --- |
| ID | Stable dispatch reference. |
| Campaign ID and Party ID | Unique together. |
| Current active token reference | Used to retrieve protected delivery material while rendering. |
| Idempotency key | Stable per campaign-party provider request. |
| Provider message ID | Persist after provider acceptance. |
| State | `Prepared`, `Queued`, `Accepted`, `Delivered`, `Failed`, `Bounced`, `Complained`, or `Suppressed`. |
| Attempt count and timestamps | Queue, accepted, delivered, and final failure timestamps. |
| Failure category | Sanitized category only; no message body or RSVP URL. |

### `EmailSuppression`

Record party or normalized email suppression with reason (`bounce`, `complaint`, or `manual`), source, and timestamps. Suppression excludes recipients from future campaigns until an approved correction workflow clears or replaces the address.

## Organizer Workflow

Add an Email campaigns workspace with these routes:

```text
/organizer/email
/organizer/email/new
/organizer/email/{campaignId}
```

### 1. Campaign List

Show campaign type, batch/scope, template version, recipient counts, state, creator, creation time, and actions to review details or retry eligible failures.

### 2. Create Campaign

Use an explicit multi-step workflow:

1. **Audience**
   - Initial invitation: one committed batch.
   - Reminder: chosen committed batch or approved explicit scope; only effectively active `Pending` parties are eligible.
   - Resend: an explicit eligible party or selected failed dispatches from a prior campaign.
   - Exclude confirmed, declined, expired, revoked-token, invalid-address, and suppressed recipients.

2. **Template**
   - Choose an approved template version.
   - Show sender identity and Reply-To snapshot.

3. **Preview and test**
   - Render HTML and plain text for representative parties.
   - Allow a clearly marked test send to an authorized test address before campaign approval.
   - A test send must not alter live campaign recipient state.

4. **Final confirmation**
   - Show final recipient count, skipped/suppressed count, batch/scope, template version, sender identity, and configured daily ceiling.
   - Confirmation creates an immutable campaign and recipient snapshot. It must not send directly in the browser request.

For E1, preparing the snapshot transitions the campaign to `ReadyForReview`; final confirmation alone transitions it to `Queued`.

### 3. Campaign Detail

Show campaign state and recipient summary. Allow authorized users to inspect dispatch state, safe failure category, provider message ID when present, and retry eligible failed records. Do not show raw token values, full RSVP links, or provider response bodies.

### 4. Party Detail

Show the latest delivery state and historical dispatches for that party. Offer:

| Action | Link behavior | Permission |
| --- | --- | --- |
| Send initial invitation | Uses current active token | Operator / ElevatedOperator |
| Resend invitation | Reuses current active token | Operator / ElevatedOperator |
| Retry failed dispatch | Reuses current active token and campaign idempotency rules | Operator / ElevatedOperator |
| Regenerate RSVP link | Revokes old token and creates a new token | ElevatedOperator, reason required |
| Send reminder | Reuses current active token, active pending only | Operator / ElevatedOperator |

## Delivery Execution

For this one-off event helper, sending is a manually triggered server-side campaign operation. Campaign confirmation persists campaign and dispatch rows transactionally; an explicit `Send campaign now` action then sends unresolved recipients sequentially. Do not send from client-side JavaScript.

The manual send operation must:

1. Process unresolved recipients sequentially and stop before the configured daily ceiling is exceeded.
2. Decrypt the protected token envelope only while rendering the individual message.
3. Call the provider through a replaceable adapter.
4. Use a stable provider idempotency key per campaign-party dispatch.
5. Persist provider message ID and normalized state before moving to the next recipient.
6. Mark transient and terminal failures as `Failed`; a later manual retry reuses the same idempotency key.
7. Avoid automatic retry for any failure category in this one-off workflow.

Use an interface such as:

```csharp
public interface IEmailProvider
{
    Task<EmailProviderResult> SendAsync(
        EmailProviderMessage message,
        CancellationToken cancellationToken);
}
```

`ResendEmailProvider` is the initial adapter. It must send a verified From address, handle provider responses without logging message bodies or RSVP URLs, and use Resend idempotency keys according to current provider documentation.

## Resend Webhooks

Before real guest delivery, add a public Resend webhook endpoint for accepted, delivered, bounced, complained, delayed, and suppression-related events when available.

The endpoint must verify provider authenticity, handle duplicate and out-of-order events idempotently, update the matching dispatch, create required suppression records, and avoid logging message content or RSVP URLs.

Provider acceptance is not delivery. The UI must distinguish `Accepted` from `Delivered`.

## Security And Privacy

- Keep the existing opaque-token and protected-envelope model.
- Persist managed Data Protection keys outside the app instance before production so delivery envelopes remain decryptable across restarts and deployments.
- Restrict envelope decryption to the send worker; ordinary organizer pages must not read raw token material.
- Do not store message bodies, raw tokens, token hashes, full RSVP URLs, query strings, provider credentials, or accessibility text in routine logs/audits.
- Make campaigns, dispatches, template approval, token regeneration, retries, and suppression changes auditable with safe actor/outcome/reason data.
- Treat recipient email and delivery status as personal data under the retention policy.

## Acceptance Criteria

1. An authorized organizer can preview and test an approved template without creating a live campaign dispatch.
2. Campaign confirmation creates an immutable recipient snapshot and one dispatch per eligible party before provider calls begin.
3. A whole-batch initial invitation sends each eligible party once per approved campaign, subject to configured limits.
4. A retry does not resend a dispatch already accepted by the provider.
5. A normal resend reuses the active RSVP link; an elevated regeneration revokes the old link and requires an explicit new send action.
6. Reminder audience selection excludes confirmed, declined, expired, locked-ineligible, and suppressed parties.
7. Email failure leaves RSVP eligibility, party state, deadline, and capacity unchanged.
8. Party and campaign views show normalized delivery status and safe failure information.
9. Bounce and complaint webhooks suppress future sends and update corresponding dispatch/party status.
10. Raw tokens, RSVP URLs, and API credentials are absent from organizer UI, audits, and captured logs.

## Phase Acceptance Criteria

### E0: Campaign Foundation

1. Sender settings, templates, campaigns, and dispatch snapshots are persisted with authorization and audit.
2. Initial campaign preparation selects only eligible committed-batch parties with active token/envelope records.
3. Each campaign-party pair has at most one dispatch snapshot.
4. The UI renders actual template versions and friendly type names.

### E1: Review And Rendering

1. A `ReadyForReview` campaign shows the exact batch, sender snapshot, approved template version, eligible count, skipped count, and dispatch list.
2. Supported placeholders render correctly for HTML and plain text; unsupported placeholders are rejected before approval.
3. Previews cover long names, diacritics, one-seat, and multi-seat allocations.
4. A test send does not create a guest campaign dispatch or change RSVP state.
5. Final confirmation requires an authorized organizer and is the only action that transitions a review-ready campaign to `Queued`.

### E2: Provider Delivery

1. No Resend API key, raw token, full RSVP URL, or rendered message body enters the database, organizer UI, audit records, or normal logs.
2. The worker can recover queued and expired-lease dispatches after restart without duplicate provider sends.
3. A dispatch uses its stable campaign-party idempotency key for every provider retry.
4. Daily quota enforcement is transaction-safe across concurrent worker instances.
5. Provider acceptance is recorded as `Accepted`, never described as delivered.

### E3: Delivery Observability

1. Campaign and party pages show normalized current dispatch state and safe failure categories.
2. Retry controls exclude accepted/delivered and terminally suppressed recipients.
3. Email outcomes do not alter RSVP status, capacity, deadline, or lock eligibility.

### E4: Webhooks And Suppression

1. Webhook authenticity is verified before processing.
2. Duplicate and out-of-order provider events are idempotent.
3. Permanent bounces and complaints create suppression records and exclude future sends.
4. `Delivered` appears only after a verified provider event.

### E5: Reminder And Resend Operations

1. A reminder targets only effectively active pending parties and respects the one-reminder policy.
2. Normal resend reuses the active RSVP link.
3. Token regeneration revokes the old token and requires an explicit replacement campaign.

## Recommended Implementation Order

1. Sender configuration and persistent production Data Protection keys.
2. Template persistence, approval, rendering, preview, and test send.
3. Campaign/dispatch/suppression schema and campaign recipient snapshot.
4. Manual initial-invitation campaign confirmation and durable worker queue.
5. Resend adapter, rate limiting, idempotency, and campaign/party status UI.
6. Party-level resend and failed-dispatch retry.
7. Manual reminder campaign selection.
8. Verified webhook processing, bounce/complaint suppression, and staging rehearsal.
